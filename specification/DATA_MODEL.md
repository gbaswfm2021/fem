# FEM data-model compliance

The fixed [FullMeta Model 2 public data-format contract](../docs/fullmeta-model-2.md) is the sole authority for `fem-model/2` field structure and meaning. Read it independently of this application specification. This document defines what the target FEM application must support and preserve; it does not provide a second field taxonomy or redefine the format through its interpreting schema.

## Required support and boundaries

The application must implement the format's required model structure and all five target profiles: `acoustic-2d`, `acoustic-3d`, `em-2d`, `em-3d` and `thermal-2d`. Cover every applicable discriminator, optional-member state, expression scope, reference, collection variant and declared result recipe. The [requirements](REQUIREMENTS.md), [UI contract](UI.md), [validation contract](VALIDATION.md) and [runtime contract](RUNTIME.md) specify the application's supported operations and observable behavior on that data.

Distinguish an editable stored representation from an executable model. Structural validity does not establish geometry support, mesh correspondence, material coverage, a valid prepared Study or numerical correctness. When an operation is outside a fixed dependency's capability, retain the representable data, report the unsupported operation and affected path, and follow the dependency boundary in [ARCHITECTURE.md](ARCHITECTURE.md). Do not reinterpret a profile, remove its data or disguise a capability failure as a format change.

The experimental `firstOrderEH` token remains the public format's explicit Study choice. It does not add a built-in EM3D Physics formulation: the built-in Physics value remains `electric`, and the required Study/Physics formulation-match check rejects an incompatible choice before dispatch. Keep structural alternatives, supported application choices and executable combinations separate.

## Application envelope and file identity

The application declares its deployment ID and relative interpreting-schema reference in the surrounding project envelope. The fixed format payload remains `modelFormat`, `metadata`, `scenario` and `model`. A particular `application` value or physical schema path is not part of the independent model format.

Resolve the project's `x-fullmeta-schema` relative to that JSON document. Preserve its selected model filename and use the canonical opened-file path for document Kernel identity. `metadata.id` retains its format-defined type, syntax and value; same-folder allocation, uniqueness, run ownership, Save and Save As follow the application lifecycle rather than redefining that model ID. See [project lifecycle](contracts/create-project-interface-contract.md) and [runtime integration](contracts/runtime-integration-boundary.md).

## Preservation and editing

- Preserve property names, JSON types, IDs, references, array order, expression text and unit tokens through Open, editing, Apply, Save and reopen. A targeted edit changes only its declared model value and the effects explicitly required by the application contract.
- Preserve optional-member absence. Show an effective default without inserting it into the saved document; do not turn a creation suggestion into a compulsory normalization. Keep explicit default-valued members when the input contains them.
- Preserve allowed additional members in the format's open objects and profile extension points. Apply the closed-object constraints where the format declares them; do not silently strip unsupported members to make validation pass.
- Keep quantity expression/unit pairs and numeric direction/vector order intact. Unit-compatible display changes must retain the declared source meaning. For external file data, preserve literal header keys and `source.columnUnits` independently of display-unit changes and apply the public format's source-unit interpretation.
- Preserve the distinction between stable IDs/condition keys and user-editable names. Rename and reordering effects follow the declared reference, scope and save contracts.
- Keep selections as ordered unions of membership-address rows, including explicit Outside members. Use the declared Keyed Choice Matrix interface without changing the persisted shape.
- Keep tree selection, controls, camera, raw drafts, validation freshness and native-operation presentation outside the model payload unless the format explicitly declares a stored value.

## Schema and evaluator realization

The target interpreting schema realizes the public format; it is not the source of new data semantics. Built-in profile schemas under `$defs.femProfiles` supply `x-fem-scenario` declarations: `profile`, `fields.formulations`, `materials` and `sweepResultQuantities`. They declare the format-consistent profile identities, formulations, mesh families, material properties and primary/derived/zero field symbols. `x-fullmeta-ui-modelEditor.scenario.defaultProfileId` selects a creation/presentation default; it does not change an existing model's profile. Shared root Study types, profile restrictions, solver-request definitions and any optional schema extensions must preserve the same stored meanings. [Profile and solver declarations](contracts/solver-capability-contract.md)

Each built-in profile schema also exposes the fixed mesher interface in its own `$defs`: `scenario.properties.profileId.const`, `scenario.properties.physics.const`, and `scenario.properties.dimension.const` must equal the corresponding `x-fem-scenario.profile` values `id`, `physics`, and `dimension`. The dimension is a JSON integer. `physicsFormulation` declares either a string `const` or a nonempty string `enum` with exactly the profile metadata's formulations. These declarations describe the same profile facts as the existing model constraints; they do not replace those constraints or change model data.

Declare a real evaluation policy with `allowDimensionlessZeroAddition: false`, `requireFiniteIntermediates: true`, and `signZeroMode: "signedOne"` under `x-fullmeta-expressionRuntime.real`. Apply it in the real runtime evaluation used by Settings and the native operations. Addition and subtraction require compatible dimensions even when an operand is zero. `sign` returns +1 at positive zero and −1 at negative zero when the evaluator preserves its sign. Verify the compiled policy separately from the declarative quantity predicate. [Validation evidence](VALIDATION.md#evidence-protocol-for-every-rule)

Browser checks use the documented Model WASM interface. The normal Validate action and native preflights apply the identified schema/validation programs at their declared stages. Geometry construction, actual mesh correspondence, material sampling, constraints and numerical solving retain checks at the point of use. Exact diagnostics, stop/continue behavior and rule evidence belong to [VALIDATION.md](VALIDATION.md); frontend or structural validation alone is not native execution evidence.

## Construction geometry acceptance

Only the domain feature variants can be group children or keys for domain membership. Apply the declared dimensional and direction checks to every eligible feature. In 2D, compile top-level `lineSegment` and `circleCurve` records as standalone curve entities alongside the 2D domains and include them in the generated geometry map. Show them in the geometry scene, but do not count them as surfaces, materials, or domain-address bits. They do not change which surface cells receive domain material assignments. Reject a construction curve nested inside a domain union/intersection with a path-specific same-dimension diagnostic. In 3D, retain the corresponding lower-dimensional construction geometry behavior. Validate, compile, and build a disposable 2D model containing a rectangular domain plus one standalone line and one standalone circle. Verify the generated geometry contains the domain and distinct curve entities, the mesh contains the domain's expected top-dimensional cells, and the curves were not reclassified as domains. Use the installed mesher capabilities for operations on curves and surfaces; report any unsupported 3D curve/surface meshing operation at the geometry stage with its feature path. A declared geometry representation remains openable and editable even where a specific meshing operation rejects it with a diagnostic. [Solver and mesher capabilities](contracts/solver-capability-contract.md)

## Native details outside the data format

The fixed native implementations consume the public Floquet phase/sign and boundary meanings; they do not define another serialized model format. Preserve consistent matrix/source reduction, prescribed-value handling, physical field reconstruction and EM3D edge/face orientation when verifying their outputs. There is no required input/output port pair, inferred incidence angle or built-in normalization of every outgoing diffraction order; use the saved source expressions and model-defined observables.

RIVRS uses a 2N real symmetric block for complex symmetric systems and an exact 4N symmetric augmentation when Floquet reduction produces a nonsymmetric operator. Faer uses complex sparse LU directly, and the RIVRS augmented path needs more memory for those cases. These are fixed native implementation details, not extra model fields or an application-side reinterpretation. Use the [native solver documentation](../fem-rust/README.md#existing-wave-solver-notes), [capability contract](contracts/solver-capability-contract.md) and [runtime acceptance](RUNTIME.md) for their actual numerical limits and evidence.

## Independent conformance cases

Create disposable examples from this contract for every profile, discriminator, and collection variant. Begin with the smallest valid document for each profile, then make focused cases for required-field omissions, optional-member round trips, each enum branch, valid and invalid references, array ordering, unit conversion, expression scope, and structural bounds. Change one value at a time for isolated checks. Add composite cases wherever two or more features interact under this contract or the application contracts, and link each such case to the behavior it covers. Application-level validation and Level 2 behavior replay consume the same case suite. Derive every case and its expected outcome from the frozen normative contracts; do not use saved project documents as test inputs or acceptance oracles. The accepted data surface is the full set of structures and meanings defined here, so an application conforming to the complete contract should interpret every conforming document consistently.
