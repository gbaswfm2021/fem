# FEM validation

This document specifies validation by purpose, inputs, predicate, stage, diagnostic, and repair. All 40 `VAL-*` functions are application-layer behavior, including checks that are reusable across unrelated applications. The model format defines the fields and meanings these checks inspect; it does not own their execution stage, message, or enforcement method. Author the selected predicates in the application schema's FullMeta programs through the Schema Editor. [Model format contract](../docs/fullmeta-model-2.md) · [Validation program designer](../../../platform/ui/widgets/validation-program/README.md)

## Rule contract

For each rule, specify the exact input paths, stage, predicate, stop/continue behavior, diagnostic, and repair guidance. A validation message must identify the model item or registration that failed. Schema validation handles JSON shape and fixed constraints; FullMeta validation handles the application's declarative cross-reference and semantic checks; the supplied native programs handle geometry topology, mesh generation, solver feasibility, numerical residuals, and generated-artifact integrity. Do not modify or rebuild those supplied programs as part of this application authoring task.

## Rule scope labels

These labels describe how broadly a predicate can be reused. They do not move its implementation out of the application layer.

The list contains 7 shared-baseline, 28 finite-element-policy, and 5 mixed rules. These numbers index this inventory; they do not prove implementation or acceptance.

## Executable model rule program

Author the application predicates under the root `x-fullmeta-rules` program as declarative requirements in the shared Schema Editor. Use program version `1` and `maximumErrors: 80` with the Model 2 envelope and declared profile context. Run structural JSON validation before the semantic rules. Allow structurally valid editor drafts and require semantic completeness at model validation and Study preparation. Declare subject scopes, predicates, dependencies and repairable diagnostic paths; the editor resolves their execution order. Declare the model ID check as the prerequisite required below. Preview, Apply, Save, reopen and inspect the authored requirements and generated bindings, then verify execution through the model validator. A configuration entry supplying a tolerance or profile choice must be read by an executable check at its declared stage. [Declarative requirements](../../../platform/docs/declarative-validation-language.md) · [FullMeta runtime rule forms](../../../platform/model-rust/README.md#declarative-validation)

The editor displays V as the length of the root `x-fullmeta-rules.rules` array. A nested assertion can belong to one top-level entry. Separate named validation programs and structural constraints such as `required` and `enum` have their own evidence. A V of zero fails application rule authoring. A positive V still requires the predicate evidence below. [Designer workflow](contracts/designer-authoring.md)

## Required validation functions

| ID | Function and purpose | Inputs and acceptance predicate | Stage and diagnostic intent |
| --- | --- | --- | --- |
| `VAL-MODEL-ID-UNIQUE` | Keep tree identity, references, and runtime lookups unambiguous across collections. | Start the model program with the shared `uniqueIds` check on the subtree under `/model`, including nested geometry, named Physics conditions, and result recipes. Each object's string `id` occurs once in that subtree. | Model. Report the duplicate ID and both object paths. Halt subsequent semantic rules on this failure. |
| `VAL-APP-PROFILE` | Keep project creation, validation, and dispatch tied to a real profile and registered runtime. | Selected project/profile exists in the schema; profile IDs are unique; selected scenario matches the model profile; the profile has a registered executable; dispatch does not target the launcher itself. | Metadata/launch/dispatch. Identify the missing or conflicting profile/runtime registration. |
| `VAL-MODEL-SCENARIO` | Match scenario identity and registration. | Read `/scenario/profileId`, `/scenario/physics`, and `/scenario/dimension`. The profile exists in the installed schema graph. Match its declared family and dimension. A caller's explicit profile or executable matches the model and registered program. | Model or launch. Identify the actual and expected identity. |
| `VAL-MODEL-GEOMETRY-NONEMPTY` | Prevent a completed simulation model with no geometry. | `/model/geometry/features` has at least one valid item. | Model/preparation. “A completed model must contain at least one geometry feature.” |
| `VAL-GEOMETRY-GROUP` | Prevent empty or nonfunctional composed geometry. | Every union/intersection group has at least two child features; each feature token has a declared validation contract and supports the scenario dimension. | Model/preparation. Identify group ID and unsupported feature/dimension. |
| `VAL-GEOMETRY-DIRECTION` | Prevent a degenerate oriented feature. | Where a feature schema declares a direction/normal vector and norm bound, its evaluated norm exceeds that bound. | Model/preparation. Identify feature and require a nonzero direction vector. |
| `VAL-GEOMETRY-QUANTITY` | Interpret geometry dimensions consistently. | Evaluate tolerance and length quantities in metres. Tolerance, rectangle and box size components, circle radius, cylinder radius and height are positive. Position and base coordinates may have either sign. The norm of a cylinder's numeric `axis` exceeds `1e-14`. | Model. Identify the feature and invalid component or tolerance. |
| `VAL-PHYSICS-CONDITION-KEY` | Keep condition identity stable for tree/settings and solver mapping. | For each Physics condition stored under a named property, that property key equals the condition's `id`. | Model. “Each Physics condition property key must equal its id.” |
| `VAL-SELECTION-ENTITY-DIMENSION` | Prevent a selection entity that cannot exist in this profile's dimension. | For `/model/selections/*/entity`, 2D allows `domain`, `boundary`, `point`. 3D also allows `edge`. | Model/preparation. Identify selection and unavailable entity. |
| `VAL-SELECTION-MEMBERSHIP-ENTITY` | Enforce membership rules for the selected entity type. | Domain rows must not contain Boundary membership. Boundary, edge, and point rows must include the Boundary state where required by the declared address format. | Model. Identify selection and address row; omitted keys remain Outside and are never rewritten. |
| `VAL-SELECTION-MEMBERSHIP-REFERENCES` | Prevent membership keys referring to nonexistent geometry. | Every membership key is a declared geometry-domain feature ID. | Model/preparation. Identify unknown feature key and selection row. |
| `VAL-SELECTION-ADDRESS-UNIQUE` | Prevent duplicate semantic addresses even when sparse maps serialize the same state differently. | Canonicalize omitted states only for comparison; each address row is unique after canonicalization. Preserve the serialized membership map and row order. | Model. Identify duplicate row indexes; do not silently delete or merge either row. |
| `VAL-SELECTION-COORDINATE` | Keep the coordinate filter evaluable. | A present nondomain `coordinateExpression` is nonblank and uses `x`, `y`, `z`, `pi`, `e`, and resolved parameters. All three coordinate symbols are valid in both dimensions. The mesher supplies `z = 0` in 2D. The zero-set expression uses numeric SI values, with geometric dimension exponents masked and the temperature exponent retained. Require a dimensionless expression result. A domain selection has no coordinate filter. | Structure or model. Point to the selection's `coordinateExpression` and name the unavailable symbol or incompatible unit. |
| `VAL-DEFINITION-IDENTITY` | Resolve expressions to unique definitions. | Definition symbols across parameters, global variables, and pointwise variables are distinct and valid. Reject reserved symbols, invalid dependencies, and unknown names. Resolve parameter values in the declared units. | Model. Name the definition and failed symbol, dependency, or evaluation. |
| `VAL-EXPRESSION-CALLABLE-ARITY` | Make expression functions predictable and diagnosable. | Verify that every advertised function in the active definition catalog has an arity declaration even when the model's definitions do not call it. Resolve each call against that catalog. `pow` requires two arguments, `min` and `max` require at least one, and every other declared built-in function requires one. Include `re`, `im`, and `conj` for dimension checking and honor the selected evaluator's supported calls. Integration calls require one eligible expression argument. | Model expression validation. Name the function with a missing declaration. For an invalid call, identify its expression path, supplied count, and allowed count or range. |
| `VAL-INTEGRATION-ALIAS-UNIQUE` | Resolve calls to one integration operator. | In a model with global definitions, check the callable aliases supplied by `/model/integrationOperators/*/id` and `/model/integrationOperators/*/name`. Deduplicate an identical ID and name on one operator. Two different operators may not claim the same alias. Perform this check even when no definition calls the ambiguous alias. | Model expression validation. Identify the alias and both operator rows that claim it. |
| `VAL-EXPRESSION-SCOPE` | Keep evaluation tied to available model values. | Use the scope in the JSON contract. Reject dependencies on coordinates, fields, frequency, or integration results unavailable to that scope. Evaluate the physical dimension against the field's unit. The built-in `t` has unit `s` and is available inside an integration argument. A global definition may declare its own `t`, which resolves normally in global expressions. Reserve the name `t` for parameter and pointwise declarations. | Model or preparation. Name the field and unavailable value, reserved name, or expected unit. |
| `VAL-RUNTIME-REAL-POLICY` | Keep numerical expression evaluation consistent with the declared target application contract. | Declare and bind the real evaluator policy with `allowDimensionlessZeroAddition: false`, `requireFiniteIntermediates: true`, and `signZeroMode: "signedOne"`. For example, a length plus a dimensionless zero is incompatible and `sign(0)` evaluates to `1`. Exercise the effective policy in each actual runtime consumer, including CAD selection coordinate filters as well as meshing and Settings. | Runtime expression evaluation. Identify the input path and incompatible dimensions or nonfinite intermediate. Record the displayed value for a valid `sign` call and the matched CAD boundary for `x-sign(0)` on a unit rectangle. |
| `VAL-INTEGRATION-OPERATOR-SELECTION` | Keep callable integration operators attached to eligible selections. | Each operator reference resolves to an existing selection whose entity matches the operator contract. | Model expression validation. Identify operator symbol and unresolved/ineligible selection. |
| `VAL-PHYSICS-DOMAINS` | Ensure Physics solves exactly the domains the model declares. | Every Physics domain ID resolves to an eligible domain selection; active domains are nonempty for profiles requiring domains. | Model/preparation. “Physics domain reference must resolve to an eligible selection.” |
| `VAL-MATERIAL-COVERAGE` | Ensure material parameters exist exactly where the active Physics uses them. | Material targets are unique and set-equal to active Physics domains; each target is an eligible domain selection. | Model/preparation. Distinguish duplicate material targets, missing coverage, extra targets, and ineligible selections. |
| `VAL-MATERIAL-PROPERTIES` | Reject unsupported or incomplete material declarations before native dispatch. | Keys, required presence, quantity or scalar representation, units, and implemented-value constraints come from the selected profile's material descriptors. Apply declared bounds after unit conversion. Thermal conductivity has an exclusive lower bound of zero in `W/(m*K)`; zero and negative conductivity are invalid. For an acoustic profile, omitting the optional `lossFactor` is valid and an explicit value must resolve to zero. | Model/preparation. Point to the exact material property and name the expected representation, unit, or implemented bound. |
| `VAL-BOUNDARY-TARGETS` | Prevent conflicting or unresolved boundary assignments. | Enabled ordinary boundary conditions have distinct targets, each resolves to an eligible boundary selection, and that condition's profile declares the required units. | Model/preparation. Identify condition and boundary selection. |
| `VAL-INCIDENT-POLARIZATION` | Ensure an incident impedance source supplies a complete vector for its formulation. | `incidentField` and `polarization` are optional together. A supplied incident field is a dimensionless complex quantity. Its polarization has one complex quantity per primary-field component in that component's declared unit. If Physics frequency is missing or invalid, check the declared source and polarization units and defer their expression evaluation until frequency is valid. | Model/preparation. Report invalid frequency at `/model/physics/frequency` and wrong units at the source or polarization component. With valid frequency, report an invalid expression at its own path. An incomplete polarization reports the required component count. |
| `VAL-MESH-SIZE-BOUNDS` | Keep global and local mesh sizing physically consistent. | `/model/mesh/minSize` and `maxSize` are positive after conversion to metres. Minimum does not exceed maximum. Each control uses a distinct target and a size within both bounds. 2D targets allow `domain` or `boundary`. 3D also allows `edge`. | Model/mesh preparation. Identify bound/control, selection, and evaluated value. |
| `VAL-PERIODIC-PAIR-REGISTRATION` | Keep the mesh-enabled periodic list consistent with declared pair objects. | Every enabled `periodicPairIds` value resolves to a `periodicPairs/*/id`; pair endpoints resolve to valid, distinct boundary selections. | Model/mesh preparation. “Enabled periodic pair IDs must reference declared mesh pairs.” |
| `VAL-PERIODIC-PAIR-COMPATIBILITY` | Ensure lower and upper mesh faces represent the same boundary address set. | Pair selections have the declared boundary entity and equal canonical membership address sets. | Mesh preparation. Identify pair and mismatching endpoint selections. |
| `VAL-PERIODIC-CONDITION-PAIR` | Prevent Physics from referencing an absent or mesh-disabled periodic pair. | Every enabled periodic condition references an existing pair enabled in the mesh list; active periodic conditions reference distinct pairs. | Model/preparation. Identify condition, pair ID, and whether the pair is absent or disabled. |
| `VAL-PERIODIC-EXCLUSIVITY` | Avoid conflicting assignments to a periodic face. | Under the declared exclusivity policy, periodic target selections do not also have an enabled ordinary boundary condition. | Model/preparation. Identify both conflicting conditions and selection. |
| `VAL-PERIODIC-PHASE` | Keep periodic phase within the solver's declared support. | Where the profile requires zero phase, each evaluated component in `rad/m` has absolute value at most `1e-12`. Thermal equality requires zero phase. Apply the supported phase policy for wave profiles. | Model/preparation. Identify condition, component, value, and tolerance. |
| `VAL-STUDY-PHYSICS` | Run the selected Study against the Physics interface it declares. | `study.physicsId` resolves to the model Physics identity; effective field formulation resolves from the Study or profile defaults and matches Physics; element order is an allowed choice. | Model/preparation. Identify Study and broken/incompatible link or option. |
| `VAL-STUDY-OPTIONS` | Use an executable combination of solver settings. | Resolve the profile's option defaults and the explicit Study values. Check effective backend, ordering, thread count, and quadrature against the formulation, order, and backend options in the Study contract. | Model/preparation. Identify missing profile defaults or the incompatible setting and allowed choices. |
| `VAL-STUDY-QUANTITY-SCOPE` | Prevent result/Study quantities from referencing unavailable expression scopes. | Every declared action quantity uses a scope allowed by the active profile and solver contract. | Model/preparation. Identify result/action quantity and unsupported scope. |
| `VAL-STUDY-FREQUENCY` | Prepare real positive wave cases. | Physics frequency and each prepared frequency evaluate to finite Hz strictly greater than zero. A harmonic parameter sweep drives the Physics frequency through its declared expression. | Model/preparation. Identify the field or case and evaluated value. |
| `VAL-SWEEP-PARAMETER` | Ensure a sweep varies a real model parameter once. | Every swept parameter resolves to `/model/parameters/*/symbol`; each symbol occurs at most once. | Model/sweep preparation. Identify unknown or duplicate parameter. |
| `VAL-SWEEP-RANGE` | Prevent a malformed or reversed sweep. | Start/end evaluate after unit conversion; end is greater than or equal to start; spacing and count are valid for the declared sweep type. | Sweep preparation. Identify the exact range field and converted values. |
| `VAL-SWEEP-INDEPENDENCE` | Make sweep values independent of iteration order. | Every linear endpoint and explicit value is independent of every parameter swept by the same Study. | Preparation. Identify the range and dependent symbol. |
| `VAL-SWEEP-CARDINALITY` | Bound resource use before dispatch. | Each axis count and the product of all axis counts are at most the declared `maximumSweepPoints`, which is 10,000 for the built-in profiles. | Sweep preparation. Report calculated count and declared maximum. |
| `VAL-RESULT-FIELD-SYMBOL` | Prevent selecting a result component that the selected solver cannot produce. | `result.quantity.component` resolves to an available field, material, or pointwise symbol for the profile/formulation. | Model/result resolution. Identify the unavailable symbol and supported symbols. |
| `VAL-RESULT-ARTIFACT` | Ensure a result view represents a real, current run output. | Selected recipe resolves to an existing artifact with matching run, Study, model snapshot, dimension, quantity, frequency/parameter filter, units, and finite data. | Result loading (runtime). Distinguish no completed run, missing file, stale model, malformed file, and mismatched result. |


The coordinate filter is applied to the union of entities selected by the address rows; it never changes address membership. A nonlinear expression is a contour declaration: the user supplies an expression whose zero set matches each intended whole entity. The mesher may evaluate it at a representative point on each address-selected CAD entity, including a curved entity, using the geometry tolerance as the absolute residual threshold. A representative-point test does not establish that an arbitrary expression vanishes everywhere on an entity. Periodic-pair checks retain their separate planar requirements.

## Evidence protocol for every rule

Use spec-derived models during authoring. For each declarative predicate, record its program pointer, input paths, passing case, isolated failing case, exact displayed diagnostic, and repaired case. An unexecuted rule or a failure masked by an earlier rule stays open. For native checks, preserve the request, executable entry, run folder, stage message, exit status, output list, and report or log.

Verify the declaration and the consumer separately whenever a rule, runtime policy, and shared control participate in the same requirement. For runtime expressions, exercise the policy with a valid scalar call, an incompatible addition involving zero, and an expression with a nonfinite intermediate. The shared declarative quantity check and the compiled runtime evaluator are separate execution paths. Record what each actually evaluates. If a frozen consumer lacks an interface needed to enforce the policy at its declared stage, record the reproduction and affected gate. [Expression and field symbols](../docs/fullmeta-model-2.md#expression-and-field-symbols)

For coordinate selection, include a 2D nondomain filter using `z`, an unknown-symbol failure, and a dimensional failure involving a temperature parameter. For callable declarations, remove an unused built-in's arity while a definition collection is active, try an invalid call count, and create two operators with a shared alias and distinct IDs. Verify that an operator whose ID and name match is still usable. Check `t` as a declared global name, as a built-in integration argument, as an unavailable undeclared name in a global expression, and as a reserved parameter or pointwise name. For incident impedance, hold the source expression constant and check it with valid and invalid frequency. Then use an incompatible incident or polarization unit with invalid frequency to verify the independent unit diagnostic.

## Registration and operation programs

Model predicates apply to project data. Author separate executable programs for the runtime stages below. Record their evidence separately from V.

| Program key | Required acceptance conditions and diagnostics |
| --- | --- |
| `x-fullmeta-metadataValidation` | Profile IDs are unique. Declared ID, dimension, Physics family, and formulations agree with scenario constraints. Field catalogs cover exactly the formulations. Material keys and symbols are unique. Field plot part declarations agree. Each built-in profile's `editorOptions` exactly matches its UI policy: acoustic and EM profiles enable global variables, pointwise variables, integration operators, periodic pairs, and parameter sweeps; `thermal-2d` enables integration operators and periodic pairs only. Scope each option-map equality to the corresponding profile ID and identify `/editorOptions` on mismatch. Identify the inconsistent profile and member. |
| `x-fullmeta-registrationValidation` | Each imported scenario profile identifies the sole runtime-profile key contributed by its scenario schema. Backend keys match nonblank `backend` values in their runtime descriptors, and each `programId` names a registered external program. Identify the profile, backend, or program ID that fails registration. |
| `x-fullmeta-dispatchValidation` | The requested profile is registered with a runtime, and the requested Study exists for operations that require one. Identify the profile or Study that cannot be dispatched. |
| `x-fullmeta-launchValidation` | The registered scenario executable resolves to a different executable from the launcher. Identify both if the route would recurse. |
| `x-fullmeta-preparationValidation` | Resolve the Study, its Physics link, and its preparation kind. Validate the required mesh and material context, enabled boundary types, active-domain coverage, and independent sweep values. Report the failed preparation contract. |
| `x-fullmeta-sweepValidation` | Call this program on each Study from the model rule program using the shared `rules` check. Check each axis cardinality and Cartesian count before enumerating cases. Report the count and limit. |

Exercise valid and invalid stage inputs from the spec. A missing or unsupported route ends with a prompt terminal error. The acceptance evaluator exercises the complete solve and result path after freeze. [Dispatch contract](contracts/solver-capability-contract.md#preparation-and-solver-dispatch)
