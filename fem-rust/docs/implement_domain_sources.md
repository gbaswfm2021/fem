# Scenario-neutral domain sources: implementation plan

> The scenario-specific test scripts and legacy numerical oracles mentioned in
> the historical verification record have been retired. Their past results do
> not establish coverage from the remaining current test suite.

## Goal and scope

Add a repeatable **Domain Source** Physics feature to all eight existing scenarios: thermal, acoustic, electromagnetic and elastic, each in 2D and 3D. A feature selects one or more domains and supplies expressions in physical spatial coordinates. Multiple features add linearly, including on overlapping domains. No feature means zero source; existing models and their results remain compatible. The feature applies to stationary and harmonic studies as supported by each scenario.

Domain Source has been implemented; the verification record below distinguishes completed checks from the broader acceptance criteria. Eigenmode studies are a later project: a driven load vector alone does not create an eigenvalue solver or separate stiffness and mass operators.

## Shared unit catalog dependency

The prior `fullmeta-core` 0.1.0 unit catalog (`platform/core-rust/src/quantity.rs`, `get_unit`) rejected `W/m^3` and `N/m^3` with `Unsupported unit “<unit>”.` A thermal heat-generation quantity and an elastic body-force density need these dimensions, respectively `[-1, 1, -3, 0, 0]` and `[-2, 1, -2, 0, 0]` in the catalog's SI dimension order. The user authorized an extension to the shared platform. The current source adds a parser for combinations of known units, allowing a scenario to declare a supported combination without a new platform build for each combination; new atomic units still need platform support. The previously deployed Store runtime does not acquire this behavior automatically. Core and model runtimes use the unit lookup in both native and browser paths, so the appropriate compatible artifacts must be built and deployed together before end-to-end verification. Existing units must not be relabeled with incompatible dimensions as a workaround.

## Contract and user experience

- Offer **Domain Source** from the PHYSICS context menu. Each entry has an independent ID, name, enabled state, domain selection and source expression components, following existing model conventions for features, selections, transactions, validation and deletion.
- Persist only user choices in the project model JSON. Absence of the collection or an empty collection represents no source. An enabled feature with an invalid or empty selection must receive a clear diagnostic according to the existing selection policy; never silently reinterpret it as all domains.
- Use existing selection references so geometry changes, remeshing and domain resolution follow the same rules as other Physics features. Reject stale, non-domain or unresolved selections. Overlap is intentional and additive.
- The scenario JSON declares the input quantity, unit, component labels and count, real or complex support, permitted expression symbols, target field and linear weak-form operation, including any coefficient and sign. These declarations drive editor presentation, validation and runtime; no profile-ID switch in the shared assembler. Define and document each formulation's source convention before assigning units or signs. In particular, 2D reductions and plate thickness conventions must be explicit; do not assume a 2D load has the same units as a 3D load.
- The generic feature mechanism is available to all scenarios, with an explicit valid source contract for every supported formulation. Do not advertise a combination until its full expression, preparation and assembly path is implemented.

## Physical contracts to define

| Scenario | Initial quantity to specify | Required review |
| --- | --- | --- |
| Thermal 2D and 3D | Heat generation density | Define source sign and the 2D thickness convention; stationary values must obey the real-valued contract. |
| Acoustic 2D and 3D | Acoustic driving source | Choose and document the physical source variable, its units and frequency factors for the pressure equation; do not assume an arbitrary RHS is a volume velocity. |
| EM 2D and 3D | Electromagnetic driving source | Define the current or equivalent source for each supported field formulation, including components, phasor convention and frequency factors. |
| Elastic 2D and 3D | Body force density | Define in-plane or three-component force and units, plus the 2D plane stress/strain and thickness convention. |

Confirm these contracts against the existing PDE notes, material conventions and time-harmonic sign convention. Where a scenario has multiple formulations, define a contract for each. Project examples and interface labels must reflect the chosen physical variables.

## Expression and integration design

1. Reuse the existing expression parser and parameter dependency handling. Compile expressions during preparation, resolve parameters for each sweep point, and evaluate at physical quadrature coordinates. Support `x`, `y` and, in 3D, `z`, subject to declared capabilities; define the handling of frequency and complex values consistently with harmonic expressions. Validate units, component count, unknown symbols and non-finite evaluations with feature and location context.
2. Resolve selected domains to mesh cells after meshing. Construct a per-cell list of active sources; preserve additive behavior and deterministic accumulation. Rebuild this mapping when the mesh or selection changes, and reevaluate parameter-dependent expressions for each sweep point.

**Implementation status:** The geometry compiler probes enabled source selections using the existing domain selection semantics; the mesher maps selected geometric entities to cells independently of material tags. Prepared solvers use that cell map for source sampling. If no sources are enabled, no source cell map is built. Thermal fixtures have verified partial and overlapping selections and mesh-cache invalidation in 2D and 3D. Full acceptance across formulations and deployments remains open.

Acceptance must include distinct selection IDs covering the same domain, a source selection spanning multiple material regions, a source selecting only part of a material, and overlapping selections with a known additive result, in both dimensions. Check the resulting assembled load and solved field, and repeat after a mesh or selection change.
3. Extend the shared volume-form contract with linear load terms. Integrate each term against the appropriate test basis using the physical integration measure and the declared coefficient, then scatter to the global RHS. Use the same orientation, component mapping and conjugation conventions as the relevant existing basis and boundary forms. Support all currently advertised scalar nodal, vector nodal and edge-based element orders; do not encode scenario names in assembly.
4. Choose a documented quadrature policy appropriate to the basis and variable expressions. Constant and polynomial examples must integrate to the expected accuracy; arbitrary expressions have numerical quadrature error, so specify available accuracy controls or limitations rather than promising exact integration.

The implementation samples Domain Source expressions at the volume quadrature points selected by the study's constitutive quadrature setting. The generic simplex rules provide `standard` and `centroid`; individual scenario formulations may restrict the permitted choices. There is no independent adaptive quadrature control for Domain Source. Spatially varying or non-polynomial expressions therefore have quadrature error; compare refined meshes and, where permitted, quadrature choices to assess convergence.
5. Apply existing periodic/weighted DOF reduction and essential boundary handling to the combined matrix and load. Include domain loads in compatibility checks for pure-Neumann or other nullspace-constrained stationary problems, including component-wise balance and relevant load scaling.
6. When there are no active sources, avoid compiling source expressions, constructing per-cell source lists or performing source quadrature. The existing sparse master matrix pattern and numerical values are unaffected by a prescribed load; reuse the existing pattern cache under its existing mesh and constraint invalidation rules. A present expression that happens to evaluate to zero may still incur evaluation cost.

## Integration work

The thermal and elastic source units require a core and model runtime that understands `W/m^3` and `N/m^3`. The current platform source can parse these as compound units, and locally built native and WASM candidates have been checked. Older checked-in browser WASM rejects them; changing only the FEM executable does not update that browser parser. A disposable native check of the same thermal model and candidate schema failed with the installed baseline DLLs (`__derived_waveMaterialSymbols` was undefined), but passed with the candidate DLLs using either the installed baseline FEM executable or the candidate FEM executable. This isolates the observed native failure to the runtime library combination; it does not prove compatibility with the previously deployed MSIX or show how that installation obtains updated browser WASM. Do not present the feature as available in that installation until it is tested there.

Browser dependency audit: FEM-owned imports now use core and model WASM bridges in `applications/fem/js/runtime`, built from the matching platform sources by `node applications/fem/js/runtime/build-wasm.mjs`. The local model bridge has its own schema-handle state, separate from the shared editor's WASM instance. The shared model editor still imports platform APIs directly: its `getUnit` is fixed to the platform core API and is used for the resolved parameter table and unit-choice filtering; shared schema editing and document transactions use the platform model API. The existing `editorDomain.resolveModelParameters` hook changes parameter evaluation but does not replace the shared editor's `getUnit`. In a browser check against the older shared platform, a thermal model and its geometry opened using FEM-local WASM, but the resolved value for a `W/m^3` parameter displayed `—`. FEM now projects the formulation's declared source-unit choices into the editor schema, preventing unrelated units in a newly added source's menu. An application-local WASM module alone does not cover every editor path. Any FEM-only solution must demonstrate these paths with the older platform, without silently degrading unit or rule validation.

FEM now updates the shared Parameters table's calculated value cells using its own parameter resolver and unit catalog; the shared editor retains responsibility for row editing and transactions. A disposable thermal project in the in-app browser displayed `2.00000` for a `W/m^3` parameter and updated it to `3.00000` after an edit. This checks the current development host with its existing shared WASM, not the exact Store-installed host. It also does not replace the entire shared table or prove the remaining shared unit-choice and native-validation paths on the Store installation.

The same disposable project saved the edit and displayed `3.00000` after reload. Its Validate button invoked FEM's declared `--validate` entry but the currently staged FEM-local DLL pair returned `Rule binding "__derived_waveMaterialSymbols" is not defined.` The staged DLL hashes differ from the tested candidate pair. The normal build plan still names the platform `lib` DLLs as build inputs, so a reproducible application-local candidate build must be established before treating deployment as verified.

## Verification and acceptance

The final Rust suite was rerun with the matching FEM-local DLLs explicitly selected: 341 tests passed, four were ignored, and two additional integration tests passed. Running against an older core DLL instead produced unsupported-unit failures for `W/m^3` and `N/m^3`, demonstrating why the matching runtime bundle matters. The automated tree-command tests exercise adding two sources, toggling, serialization, and guarded deletion for every declared scenario formulation; they do not replace browser lifecycle tests for each formulation.

FEM-local model WASM validation was also exercised with generated fixtures for every declared formulation: a valid source passes, and a malformed expression, an unknown symbol, an incompatible unit, and a stale domain selection each produce validation errors. This verifies the shared validation path for all formulations; it does not claim that each diagnostic was inspected visually in the browser.

For repeatable local test runs, select the matching `fullmeta_core.dll`, `fullmeta_model.dll`, and `fullmeta_operation_contracts.dll` via `FULLMETA_CORE_DLL`, `FULLMETA_MODEL_DLL`, and `FULLMETA_CONTRACTS_DLL`. On this Windows machine the tested Rust toolchain is `stable-x86_64-pc-windows-gnu`; the default MSVC toolchain does not have its linker configured.

- Schema and UI: create, edit, disable, delete, save and reload multiple features; verify selection, component widgets, units, invalid expressions and stale domain diagnostics across all eight scenarios. Confirm old models with no sources remain valid.
- Assembly: compare constant and spatially varying local loads against analytic integrals for each supported basis, dimension and order; include vector components, complex coefficients, element orientation, overlapping sources and disjoint domains. Check quadrature convergence for non-polynomial expressions.
- The scalar tests include analytic triangle and tetrahedron loads and a non-polynomial manufactured thermal solution under refinement. The vector tests compare body-force displacement against independent one-element results for plane stress, plane strain, and 3D elasticity. For first-order edge elements, the assembled complex load and the source-driven change in the solved degree of freedom match closed-form one-element values under two local tetrahedron orientations. The second-order edge test independently integrates its quadratic basis via exact tetrahedral polynomial weights and compares the result under the same orientations. The source declarations' signs and frequency factors are checked for every supported formulation.
- The second-order edge test also compares a complex source varying linearly with physical `x` against an independent degree-three tetrahedral integration rule, for both tetrahedron orientations. The constant and spatial checks exercise the same periodic reduction as the production assembly.
- The configured EM3D first-order current-source path also matches an independently assembled complex three-unknown tetrahedron solution, including the declared permeability, permittivity, conductivity, and frequency factors. The second-order configured path is checked for a nonzero driven field and a zero field with the source removed.
- Acoustic 2D has a spatially varying source compared against an independently integrated center-node solution, and acoustic 3D has a constant-source tetrahedral solution. EM 2D tests both `Ez` and `Hz` against independent center-node values in the near-zero mass-term limit. These complement the thermal, elastic, and EM 3D checks above.
- Source-driven disposable release studies have completed for all eight scenarios. Additional runs cover both EM2D formulations, both elastic-2D formulations and EM3D orders 1 and 2. These runs establish successful nonzero responses, not independent analytical accuracy for every formulation.
- The subsequently built four-file FEM-local bundle identified above also completed source-driven studies for all eight profiles: thermal 2D/3D, acoustic 2D/3D, elastic 2D/3D, and EM 2D/3D. Each test used its matching core, model, and operation-contracts DLLs and checked for a nonzero primary field.

- Sweeps and topology: change parameters, frequency, selection and mesh; verify source expressions and domain mapping update. Compare results with a fresh assembly and ensure sparse-pattern reuse never retains stale topology.
