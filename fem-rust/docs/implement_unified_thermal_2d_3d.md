# Plan: unify thermal 2D and 3D without losing functionality

## Objective and scope

Bring `thermal-2d` and `thermal-3d` to the same functional standard while keeping their configuration in scenario JSON and their numerical execution in shared, scenario-neutral FEM infrastructure. Preserve existing project files, boundary and source meanings, sparse assembly, solver choices, and supported results. A new scenario using an already supported generic formulation should not require a new scenario-specific assembler or a profile-ID switch in shared Rust or UI code.

This is an implementation plan, not a claim that the proposed parity is already implemented. It covers the FEM application, its scenario contracts, the generic runtime and the related documentation/tests. It does not introduce an eigenmode study, transient heat transfer, arbitrary spatially varying thermal conductivity, nonzero-phase thermal periodicity, or additional element orders. Those features need separate contracts and acceptance work.

## Findings and baseline

- The common physical model is stationary scalar conduction, `q = -k grad(T)` and `-div(k grad(T)) = Q`. Both scenarios use order-1 nodal scalar elements, positive material-wise conductivity, a real stationary solution, Dirichlet temperature, outward normal Neumann flux, additive Domain Sources, and a component-mean reference for compatible unanchored systems. Both declare Faer and Rivrs backends.
- Thermal 2D uses triangles and a per-unit-out-of-plane-thickness convention; thermal 3D uses tetrahedra and physical volume. Shared mathematics does not mean pretending these measures, output units or geometries are identical.
- In the inspected checkout `thermal2d.json` is approximately 1.09 MB and `thermal3d.json` approximately 18 KB. Most of the extra 2D data is `schemaContributions`, including authored declarative validation and a much larger executable rule AST; pretty printing amplifies the difference. This is not evidence that 3D assembly is missing.
- Some rules in the 2D package are thermal-family or general rules, not exclusively 2D rules. With all packages composed, invalid thermal Study types and invalid thermal boundary expressions are diagnosed for 3D; a focused composition check without `thermal-2d` showed those particular diagnostics disappear. The current semantic material-quantity rule for positive conductivity is scoped to `thermal-2d`: a `-1 W/(m*K)` value produced its diagnostic in 2D but not in the 3D model-rule check. Both scenario material bindings declare a positive bound, which is checked by the solver, so distinguish model-validation timing from solver acceptance.
- 2D currently supports zero-phase matched-node periodic conditions and scalar or two-component vector heat-flux input. 3D explicitly rejects periodic pairs and uses scalar normal flux. These are actual capability gaps, not file-format differences.
- 3D declares volume, boundary area and outward boundary-power outputs; 2D does not declare corresponding length, area and per-unit-depth power summaries. Other current policies differ, including mesh format, facet ownership, topology tolerance, residual tolerance and recovery options. Investigate each before changing it: some may be intentional compatibility or dimensional choices.
- Browser composition regenerates executable validation rules from declarative obligations. The native scenario runtime also merges executable rule arrays. Do not simply remove the generated rules or assume the browser and native composition paths are equivalent.

Before changing anything, record the exact source revision, scenario JSON and base-schema hashes, active native executable and matching DLL/WASM hashes, toolchains, and representative saved output schemas. Capture the current test results and baseline models generated independently from the public format. Existing implementation notes include [2D thermal](notes_thermal2d.md), [3D thermal](therm3d.md), [Domain Source](implement_domain_sources.md), and [scenario-neutral assembly](implement_scenario_neutral_assembler.md).

## Target behavior

| Area | Common standard | Dimension-specific contract |
| --- | --- | --- |
| Study | Stationary conduction, real-valued inputs and solution, same mean-temperature and nullspace behavior, supported Faer/Rivrs options. | 2D triangles and 3D tetrahedra; preserve existing supported quadrature and order restrictions. |
| Materials | Required scalar `thermalConductivity`, compatible unit and finite positive evaluated value; parameter-only material scope unless separately extended. Equivalent diagnostics in editor, preparation and solver. | Selection geometry and integration measure differ. |
| Domain Source | Zero when absent or disabled; multiple selected-domain sources add, including overlaps. Real `Q` in `W/m^3`, parameter and supported spatial-coordinate expressions, evaluated at physical volume quadrature points. | 2D load and energy balance are per unit depth; 3D uses volume. |
| Boundaries | Prescribed temperature; scalar outward normal flux; vector heat-flux components projected onto the outward normal. Retain scalar and vector input compatibility, with a zero companion scalar where the existing contract requires it. | `qx, qy` in 2D; `qx, qy, qz` in 3D. Integrals use edge length or surface area. |
| Periodicity | Matched-node zero-phase periodic identification; consistent mapping of temperature, constraints, sources, mean gauges and mesh changes. Reject unsupported nonzero phase with a clear diagnostic. | Pair edges in 2D and faces in 3D, using the dimension-specific geometry and mesher representation. |
| Results | Preserve all existing fields, CSVs, names and consumers. Offer comparable domain measure, boundary measure and outward heat flow/energy-balance summaries, clearly labeled with physical units and 2D thickness convention. | Area and boundary length in 2D, volume and boundary area in 3D. A 2D integrated flow is per unit out-of-plane depth unless an explicit physical thickness is part of a future contract. |
| Validation | Common semantic rules must apply in either scenario independently, with equivalent unit, expression, Study, selection and runtime checks. Adding a scenario must not silently depend on another scenario being registered. | Profile metadata, coordinate scope and allowed boundary component counts derive from the selected scenario. |

Do not advertise a new capability in the UI or scenario JSON until validation, preparation, generic assembly, output handling and end-to-end checks are implemented together. Retain currently accepted behavior while rolling out stronger validation: identify and document any previously accepted invalid models, keep old valid models valid, and give actionable diagnostics.

## Design principles

1. **One generic mechanism, explicit declarations.** Keep physical quantity, unit, input layout, coefficients, signs, spaces, integration and output recipes in scenario data. Shared code interprets declared capabilities and dimension; it must not branch on `thermal-2d`, `thermal-3d`, or future scenario IDs.
2. **Shared validation ownership.** Define how a scenario or common application contract declares reusable validation once. Separate truly profile-specific metadata checks from general Physics, material, Study and boundary checks. The design must work when either thermal scenario is registered alone, as well as alongside all other scenarios. Keep error paths, diagnostics and runtime semantics equivalent across browser and native validation.
3. **One authoritative source for validation rules.** Investigate how to produce the native executable AST from declarative obligations deterministically at build/composition time while retaining compatibility with the existing public schema and deployed host. Generated artifacts may be retained where required, but their provenance and freshness must be mechanically verified. Do not delete executable rule arrays before native parity is demonstrated; do not hand-maintain divergent copies.
4. **Sparse throughout.** Continue using the shared sparse master-matrix and weighted reduction infrastructure. Domain loads only alter the RHS. Cache only topology-dependent patterns and invalidate when connectivity or representative maps change; update numerical coefficients, source samples and weights for each case. Never introduce a dense global matrix.
5. **No hidden compatibility change.** Keep current model JSON identifiers, units, signs, optional-field absence, unknown extension data where supported, result filenames/keys and behavior for source-free projects. Add result fields rather than silently renaming or reinterpreting existing ones. Support both current mesh formats where required until migration and consumers are verified.
6. **FEM-owned deployment.** Maintain the tested matching FEM-local native DLL and browser WASM bundle, and the ability to host the FEM application on the archived older platform. Any unavoidable shared-platform interface change must be identified, authorized and compatibility-tested; avoid requiring a new installed Store platform merely to use these FEM features.

## Implementation stages

### 1. Freeze behavior and trace ownership

- Inventory and compare both complete JSON contracts, effective composed schemas and their executable validation programs. For every rule record whether it is genuinely common, profile-specific, duplicated or currently owned by the wrong scenario. Include model, metadata and preparation validations; browser and Rust composition; schema/UI projection; and selection, Study and result capabilities.
- Establish source-free and source-driven baselines for each dimension, both backends where available, current scalar and 2D vector boundary inputs, 2D periodicity, mean constraints, mesh cache, and outputs. Record exact acceptance criteria and tolerances before comparing changes. Preserve the existing staged runtime and backups for an independent baseline.
- Catalog policy differences (`meshFormat`, facet ownership, determinant tolerance, residual tolerance, recovery and output settings). For each, document its rationale, supported inputs and effect. Preserve the prior behavior by default until equivalence or a deliberate compatible extension is demonstrated. A stronger check must not quietly reject previously valid cases.

### 2. Factorize common validation and scenario declarations

- Design a scenario-neutral shared validation contribution or template mechanism. It must express family-independent rules using declared property descriptors and capabilities, not a new list of hard-coded profile IDs. Keep profile identity, dimension, available components and supported features in each scenario JSON; keep shared mechanics in generic FEM-owned infrastructure.
- Relocate or generate general rules now carried by thermal 2D, including thermal Study type and boundary quantity/scope checks, without removing unrelated wave or global-expression validation currently contributed by the same package. Preserve metadata and preparation obligations that are truly profile-specific.
- Derive material presence, expected unit, allowed expression scope and bounds from the active scenario's material declaration for both thermal dimensions. Validate positive finite conductivity consistently, and report its model path. Do not assume the same rules for every future material property: the declaration must control them.
- Ensure scenario composition independently supports 2D only, 3D only, both in either registration order, and all eight existing scenarios. Detect duplicate/conflicting rule IDs, bindings, defaults and metadata instead of silently dropping or changing them. Confirm disabling/removing one scenario does not remove another's necessary rules.
- Establish a deterministic generation/freshness check for declarative obligations and native AST. Compare effective browser and native rules using the same valid and invalid cases. Preserve installed-package operation where source build tools are unavailable.
- Reduce duplicated JSON only after these checks pass. Compare compact semantic content and generated/runtime behavior, not raw file sizes alone. Document the remaining dimension-specific differences and any generated files.

### 3. Add 3D vector heat flux using the existing generic form

- Declare the 3D Neumann vector input, Cartesian labels, units, component count and normal-trace weak form in `thermal3d.json`, following the existing data-driven 2D pattern. Extend generic adapters only where a dimension-independent capability is genuinely missing.
- Integrate `-integral(test * n·q) dS` using the outward normal of the adjacent tetrahedron. Preserve the existing scalar outward-flux sign and parameter-only boundary-expression scope. Check component count, real values, unit compatibility, non-finite values and the companion-scalar rule. An omitted vector retains the existing scalar meaning.
- Validate normal orientation under vertex permutations and correct behavior on all exterior faces. Preserve current treatment of internal facets unless a separately justified change is tested and documented.

### 4. Add zero-phase periodicity to thermal 3D

- First audit the existing dimension-neutral mesh-pair, matched-node and weighted-reduction capabilities for triangular faces, multiple pairs and 3D corner/edge intersections. Implement missing generic matching, translation, topology and constraint functionality before changing the scenario's advertised flags. Do not create a thermal-specific periodic branch.
- Declare supported pair types and zero-phase policy in the 3D scenario. Validate mesh-pair activation, one-to-one node/face matching, translation and tolerances, conflicting/overlapping ordinary boundaries, duplicate constraints, nonzero or invalid phase, and matching model/mesh-map data.
- Apply periodic identification to the sparse matrix and all RHS contributions, including multiple Domain Sources and boundary loads. Preserve consistent Dirichlet handling and component-wise pure-Neumann compatibility/mean-temperature gauges after identification. Invalidate relevant mesh and master-pattern caches on geometry, mesh, pairing or constraint changes.
- Preserve 2D periodic behavior, including its accepted tolerance and conflict checks. Enable the 3D UI action only after native solve and compatibility tests pass.

### 5. Align result observability without changing meanings

- Define a dimension-aware result contract for area/volume, boundary length/area, outward integrated flux and net heat balance. In 2D, make per-unit-depth quantities and units explicit; do not label a cross-sectional quantity as total 3D power. Preserve 3D's existing output keys and units, and add compatible 2D fields or a versioned extension rather than changing old fields.
- State whether reported boundary flux is an input integral or a recovered, cell-based approximation. When sources are present, the physical conservation comparison is integrated outward flux versus integrated generation, not necessarily zero outward flux. Document discretization and recovery limitations.
- Check field/result consumers, charts, summary CSVs, integration operators and old saved results. Do not claim a new results workflow solely because a quantity is present in a JSON output.

### 6. Integrate and document

- Update both scenario JSONs, scenario registry/capability declarations where appropriate, and only the generic FEM infrastructure needed to interpret the new contracts. Keep the assembler neutral and retain its existing no-active-source fast path.
- Update the public FEM model/schema and editor annotations only when needed for a shared, declared capability; keep scenario-specific meanings and defaults in scenario packages. Update the FEM specification, user guide, `notes_thermal2d.md` and `therm3d.md` with equations, units, 2D depth, source and boundary examples, periodic limits, result meanings and migration notes.
- Build matching FEM-local native and browser runtime artifacts with the documented application build. Produce a reviewable package without installing it over the user's Store application. Record hashes and the exact archived platform version used for compatibility testing.

## Verification and acceptance gates

Each gate records inputs, expected result, candidate identities, actual result, tolerances and artifact locations. A test with a partial result does not establish the entire gate. Fix failures and rerun affected checks; preserve evidence for unaffected identities.

1. **Contract and validation parity.** Test both profiles with all packages, 2D alone and 3D alone. Check required/positive conductivity, real quantities, dimensions/units, valid and invalid symbols, `x/y/z` scope, finite values, selected domains and stale references, Study types and solver settings. Test enabled/disabled features and malformed declarations. Compare browser-local WASM and native validation, including missing/duplicate rules, and confirm equivalent error paths and meanings.
2. **Boundary equivalence.** For 2D and 3D, compare a constant Cartesian flux vector with the analytically equivalent scalar normal flux on each differently oriented facet. Test non-axis-aligned facets, orientations/permutations, complex or invalid values rejected for stationary thermal, inconsistent companion scalar, omitted vector, zero flux, and coexistence with temperature and Domain Sources. Compare local load vectors and solved fields.
3. **Periodic and constraints.** Test a 3D box with one and multiple matched face pairs and shared corner/edge nodes, with zero phase. Compare the reduced sparse system and fields with an independently constructed reference. Cover incompatible matches, nonzero phase, boundary conflicts, incompatible Dirichlet values, multiple disconnected components, balanced and unbalanced Neumann/source loads, and mean constraints. Rerun established 2D periodic tests unchanged.
4. **Domain sources and integration.** In both dimensions test constant and spatially varying sources against independent local integrals and manufactured or analytic solutions; test overlaps, distinct IDs for the same domain, a partial material region, a source spanning multiple materials, absent/disabled sources, and additive boundary loads. Check convergence for non-polynomial expressions and document quadrature limitations.
5. **Sparse cache and sweeps/topology.** Assert sparse matrix structure and values remain unchanged when only a source is added or removed. Compare reusable and freshly built assembly/reduction for altered connectivity, representative maps and numerical weights. Change geometry, mesh size, selection and periodic pairs; verify no stale cell mapping or master pattern survives. Although thermal studies remain stationary, exercise parameter changes between separate solves and all relevant shared cache interfaces.
6. **Output and compatibility.** Compare old and new source-free fields, fluxes, summaries and preserved keys against the identified previous executable; verify new measures and signs independently in both dimensions. Test old models and saved results, optional/unknown data preservation, both backends, documented mesh formats and meaningful topology tolerances. Inspect representative result UI, including units and 2D per-depth labels.
7. **End to end and performance.** Through the editor create, edit, disable, save and reopen sources and scalar/vector/periodic boundaries in both dimensions; validate, mesh and solve a stationary Study and inspect outputs. Repeat appropriate cases with the identified archived Store platform and the new FEM-local bundle. Compare release-build source-free and source-enabled timings on the same representative meshes, separating preparation, assembly and solve where instrumentation permits. Report sample size and any measured regression; do not infer scaling from a tiny fixture.
8. **Documentation and packaging.** Check links and consistency among scenario notes, model format, specification and UI. Verify the packaged schema, scenario data, executable, three matching DLLs and FEM-local WASM modules, and confirm the executable identity matches the tested candidate. Distinguish archived-platform testing from testing an actual installed Store release.

## Completion criteria and rollout

Complete the work only when both thermal profiles meet the target table, existing supported behavior and result contracts have been regression-tested, all applicable gates pass on the same identified candidate, and any limitations are documented. Measure the JSON reduction after factorization, but treat smaller files as a consequence rather than the acceptance criterion. If a shared dependency or unsupported numerical case prevents a gate, record the exact version, reproduction, diagnostic and affected capability; keep it unadvertised and the gate open. Deliver the changes and evidence for review before any installation or public release.

## Implementation checkpoint

- Thermal-only browser composition no longer imports wave obligations from the 2D thermal package. The equivalent native wave executable rules are carried by the wave packages, after their required derived bindings. Thermal 3D carries compiled and declarative thermal validation, including positive conductivity. Common rules are authored in `validation/thermal-common.json` and copied into each independently deployable scenario package; the FEM build checks that both copies are current. Use `node prebuilt-tools/sync-thermal-validation.mjs --write` to regenerate them after editing the shared source.
- The 3D scenario declares scalar and vector Neumann inputs. Focused tests compare vector and scalar normal loads, including an oblique face and tetrahedron vertex permutations, and exercise the tree default and expression validation. A larger end-to-end editor and packaged-runtime acceptance remains open.
- The 2D result contract declares area, boundary length and recovered outward power per unit depth using existing shared result values. The result-plan interpreter has a focused test; saved-results and result-UI compatibility remain open.
- The generic 3D periodic matcher checks that the node correspondence also maps triangular-face connectivity. Tests cover intersecting matched pairs, incompatible diagonals, nonzero phase and tetrahedral periodic solves with and without a constant Domain Source, as well as a mean gauge and conflicting prescribed boundary. Thermal 3D now declares zero-phase matched-node periodicity. A real Gmsh box and the old-host test below exercise the mesh and editor paths.
- An isolated release candidate and matching DLLs were built under `target/fem-local-bundle/x86_64-pc-windows-gnu/release`; they have not been staged over the active runtime. The candidate DLLs pass the native unit suite, while the older staged development core DLL rejects the `W/m^3` Domain Source unit. The copied installed Store host `Mimicot.FullMetaPlatform` version `0.2.2.0` validated, meshed and solved independently authored 2D and 3D stationary models with periodic pairs and Domain Sources. The candidate application used the same scenario JSON, base schema and FEM-local WASM hashes as the source checkout. On coarse meshes the maximum temperature errors versus the analytic slab solution were 0.0058 K in 2D and 0.0100 K in 3D; the 3D periodic matched-node temperatures agreed exactly. The 2D area and 3D volume were 1 m² and 1 m³. The reported boundary power is recovered cell flux, not an exact conservative flux; the coarse 2D and 3D values were 0.812 W/m and 0.883 W against source integrals of 1 W/m and 1 W respectively. Source-free old-versus-candidate solves on the same meshes differed by 0 K in 2D and at most 1.2e-13 K in 3D. Performance and exhaustive saved-result compatibility have not been established.
