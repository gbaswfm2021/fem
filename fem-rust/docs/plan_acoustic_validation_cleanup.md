# Plan: acoustic validation cleanup and parity

## Objective and scope

Remove validation duplication between layers in `acoustic2d.json` and `acoustic3d.json`, correct the misplaced compiled `Hz` metadata rule, and validate acoustic Neumann vector lengths before a Study reaches the solver. Preserve the supported models, validation entry points, diagnostics where they are part of an observable workflow, and the scenario-neutral assembler. This is a plan, not a claim that the changes or acceptance checks have been completed.

Duplication between the two acoustic scenario packages is acceptable. The goal is to avoid maintaining the same check at multiple layers without a reason, not to remove a rule solely because it appears in both files. A check at model-validation time and a second check on sampled solver inputs may both be necessary: they run at different times and may see different values.

Keep acoustic-specific declarations in the scenario packages. Any new interpretation must be a generic, declaration-driven capability, usable by other applicable scenarios without profile-ID switches. The shared assembler and sparse matrix behavior are outside the intended change. Do not change the platform, Schema Editor or installed Store app to accomplish this work; if a necessary generic interface is missing, document and test the smallest FEM-owned solution or record the exact dependency and affected acceptance gate.

## Findings to verify against the implementation baseline

1. The composed material schema for each acoustic profile requires `density` and `soundSpeed` and rejects properties not declared by that profile. Focused structural tests rejected omission of either required property and the presence of each of `relativePermittivity`, `relativePermeability`, `conductivity` and `thermalConductivity`. The six corresponding semantic obligations therefore overlap with structure validation **in the normal schema-first model-validation path**.
2. Semantic rules can also be called directly. Removing those six obligations would alter that entry point and its diagnostics unless another check preserves them. Structural errors may also have different wording and ordering. Do not call the overlap a safe deletion until the observable contracts are inventoried and tested.
3. Both acoustic packages declare `incident_polarization_count_electric`, although its condition applies to the `electric` formulation. Equivalent declarative and compiled rules were found in the electromagnetic packages. Removing acoustic copies is a candidate, subject to independent and combined registry tests and comparison of compiled rules.
4. Both acoustic packages contain two additional compiled metadata rules for `pressure` and `Hz` element orders beyond the ten authored metadata obligations. The compiled `Hz` check also appears in the electromagnetic packages, while no matching authored obligation was found in the inspected packages. In a focused native-style metadata program using only an acoustic profile, the acoustic copy reported that the absent `Hz` formulation must declare order 1; the browser-generated metadata program did not contain that check. This demonstrates a declaration/compiled-program mismatch; it is not yet a complete test of every native executable and installed package combination.
5. The acoustic `boundaryInputs.pressure.neumann.prescribed.vector` declarations require two components in 2D and three in 3D. The generic boundary-input compiler rejects the wrong count during solver input preparation. Focused model-rule checks did not reject a single-component vector. The ordinary scalar form is valid when `fieldValues` is absent; when the vector is present, the accompanying scalar must be zero. The vector entries are complex-capable `m/s` expressions sampled at boundary points.
6. `material_quantity_density` and `material_quantity_soundSpeed` also validate expression symbols and units; an unknown symbol passed the structural material fragment but failed the semantic rule. Keep the expression checks. Both declarations currently specify **nonzero**, not positive, solver values: do not introduce a new positivity policy for density or sound speed in this cleanup. The optional acoustic loss factor is declared implemented only at zero; retain both early and runtime enforcement until their roles are proven equivalent.

## Target behavior and compatibility

- Valid existing acoustic 2D and 3D models continue to validate and solve, including models with scalar Neumann values and no `fieldValues`, valid complex and coordinate-dependent vector expressions, frequency-dependent materials, multiple boundaries, periodic pairs and Domain Sources.
- An enabled Neumann boundary with a present `fieldValues` array must have exactly the component count declared by its selected scenario/formulation. Acoustic `pressure` currently declares two in 2D and three in 3D. Errors identify the boundary and `fieldValues` path and state the expected count. Preserve component order, existing `m/s` expression checks, normal projection, scalar/vector selection and zero-companion behavior.
- Respect existing treatment of disabled conditions and absent optional fields. In particular, do not impose an unconditional JSON Schema `minItems`/`maxItems` that rejects a disabled legacy condition if the current contract skips it. Determine existing behavior at every entry point first; any stricter handling of disabled or previously accepted models must be explicit and justified by the test matrix.
- Normal model validation and any supported semantic-only or declaration-validation APIs continue to report the same invalid cases. Preserve established error paths and messages where consumers or documented workflows rely on them; where a structural and semantic error differ, record the old and new behavior and require equivalent actionable diagnostics. Do not silently discard independent semantic-only checks to make a package smaller.
- Acoustic-only 2D, acoustic-only 3D, both acoustic packages in either order, each electromagnetic package independently, and all eight packages together must compose and validate without requiring an unrelated profile. The `Hz` metadata requirement remains effective when a scenario actually declares that capability; it must not require an acoustic-only registry to install `Hz`.
- Keep existing project JSON property names, defaults, result files, unknown extension data where supported, sparse assembly, cache semantics, backends and Store-host compatibility. New validation rejects a wrong-length **enabled** vector earlier; this is an intentional improvement for inputs already rejected by the solver, not an assertion that all previously accepted models are invalid.

## Implementation stages

### 1. Freeze the baseline and map validation ownership

1. Record the active candidate executable and matching core/model/contracts DLL and FEM-local WASM hashes, scenario JSON and base-schema hashes, registry, toolchain, and the installed Store-host version when available. Preserve an isolated copy of the pre-change candidate; do not overwrite the running server or the user's projects. The last thermal work built a separate candidate and exercised Store host 0.2.2.0, but re-identify the actual artifacts rather than assuming they are still current.
2. List all authored obligations and executable rule AST entries in both acoustic packages for model, metadata and preparation stages. Record the owning package, exact condition, scope, diagnostic, dependencies/exposed bindings and whether a rule is duplicated in another package or in the composed structural schema. Match compiled rules by stable IDs/provenance or normalized content and diagnostics, not by assuming authored and compiled array indices are the same: acoustic metadata currently has 10 obligations and 12 compiled entries.
3. Trace every supported caller of structure validation, `validateModelRules`/semantic-only validation, native model validation, metadata validation, preparation and boundary-input compilation. Record which callers run structure first and which expose only one stage. Inspect browser composition, which recompiles obligations, and native composition, which merges executable ASTs. Include ordering, duplicate elimination, exposed bindings and error limits.
4. Capture baseline behavior for valid, invalid and disabled synthetic models. Create disposable fixtures from the documented format; do not inspect or copy user projects. Include both dimensions and an unrelated pressure-independent scenario so that shared machinery is not accidentally specialized to acoustics.

### 2. Consolidate the six material checks without weakening an entry point

1. Verify that browser and native schema composition construct equivalent per-profile material schemas: `density` and `soundSpeed` required, and the four named unrelated properties disallowed for both acoustic dimensions. Check other known and unknown material properties and the existing unknown-extension policy, rather than assuming `additionalProperties: false` has identical effects in every context.
2. For each of the six obligations, compare full model validation, structure-only validation and supported semantic-only calls before and after an **in-memory** removal. Record acceptance, diagnostic path, message and ordering. In full schema-first validation verify whether the semantic obligation is reachable at all when the structural error is present.
3. If semantic-only validation is a supported contract, retain equivalent behavior by deriving a generic semantic material-presence/exclusion check from the active scenario's material declarations, or by retaining the existing obligations for that entry point. Prefer a shared declared mechanism that avoids a second manually maintained list; do not hard-code the two acoustic IDs. Verify that generic derivation respects required/optional properties and the actual extension policy for all affected profiles.
4. Remove each redundant acoustic declarative obligation **and its matching native executable AST** only after its behavior is provided by the authoritative layer for every supported caller. If a direct-call contract or diagnostic cannot be preserved without a broader change, keep the rule and record the reason instead of claiming it is redundant. Do not remove `material_quantity_density`, `material_quantity_soundSpeed`, or the zero-loss check as part of this deletion.
5. Maintain deterministic authoring and generation for retained/moved ASTs. A build or test must fail on stale generated data. Treat the authored rule and its compiled representation as two deployment forms of one check, not as two independent model checks to delete.

### 3. Correct metadata ownership and browser/native parity

1. Identify the authoring source and all owners of the compiled `pressure` and `Hz` rules. Establish whether they were intentionally shared global capability checks or stale generated remnants. Compare the native merged program with the browser-generated program and the metadata input actually supplied by the native context.
2. Make the `Hz` check conditional on a declared `Hz` capability or keep it under the package that declares that capability, using a generic capability mechanism. Remove the acoustic copies only when the independent electromagnetic scenarios retain their own required validation. Do not make a new `if acoustic`/`if EM` dispatch in Rust or UI code.
3. Preserve a valid check for acoustic `pressure` order 1. Confirm the acoustic weak-form, mesh and Study declarations agree. Do not delete the pressure rule merely because it is adjacent to the stray `Hz` rule.
4. Restore a single authoritative relationship between metadata obligations and executable ASTs. Generate the relevant native ASTs deterministically from their declared source, or document a generic generated source for intentionally non-obligation metadata checks; add a freshness/parity check. Do not blindly truncate the compiled metadata array to the number of obligations.
5. Re-run acoustic-only and electromagnetic-only metadata validation in the real native path, plus browser composition. Check the full registry and both registration orders. A single-profile browser test or a simulated native merge alone is insufficient to establish the native gate.
6. Assess the three `metadata_scenario_acoustic_*` checks separately. The current composition constructs scenario choices from profile metadata, but determine whether supported imported/custom schema paths can bypass that construction. Remove a check only if all supported entry points retain the same protection and diagnostics; otherwise keep it. Preserve the remaining package identity, catalog and editor-option checks unless independently demonstrated redundant.

### 4. Validate Neumann component count from the scenario contract

1. Trace the vector input contract, editor layout and default for every scenario that uses `boundaryInputs`, including optional vectors, `fallbackPath`, scalar/vector alternatives and disabled conditions. Establish the authoritative count from the active formulation's `prescribed.vector.components`, rather than a hard-coded `acoustic-2d`/`acoustic-3d` branch or a second independently authored count. Check that layout shape and default-vector length agree with that declaration; reject malformed scenario declarations with a clear package diagnostic.
2. Implement a scenario-neutral model-validation mechanism that uses this declaration for applicable enabled conditions. Consider a generated per-profile structural constraint only if it can preserve optional-vector absence, disabled-condition behavior, alternate input paths and all other scenarios' existing semantics. Otherwise use a generic declared semantic obligation. The choice must work in both browser composition and native validation and must not require a shared-platform change or a scenario-specific assembler branch.
3. Require an array of exactly the declared length when the selected vector is present. Keep legacy scalar-only Neumann rows valid, including nonzero scalar outward velocity; do not auto-add or truncate components in existing project data. Maintain the current vector precedence and zero companion scalar, complex expressions, coordinate/frequency scope and unit checks. Keep the generic solver's count check as a defensive runtime guard for direct solver requests and malformed inputs.
4. Test one-short, one-long, empty, non-array and correct-length values, absence of `fieldValues`, disabled rows and enable/disable transitions. Check 2D and 3D separately, plus a non-acoustic vector scenario to confirm the mechanism is generic. Check `fallbackPath` and `scalarOptionalWhenVector` where a scenario declares them; do not assume acoustic's particular layout is universal.
5. Ensure count diagnostics identify the item and property consistently in schema-first, semantic-only where supported, browser-local WASM and native preflight. Reopen old valid models and verify vector defaults and labels. Invalid projects should be editable so users can correct them; do not rewrite or silently discard their drafts.

### 5. Remove the inapplicable electric rule and integrate documentation

1. Remove `incident_polarization_count_electric` from the acoustic authored obligations and the corresponding compiled executable rule only after proving the `electric` formulation cannot be selected in acoustic profiles and both electromagnetic packages retain the necessary rule for independently registered execution. Check whether shared-program consumers depend on an acoustic package supplying it; if they do, first move ownership to a generic wave contribution or retain it.
2. Verify other incident-field, boundary, frequency, global-expression and preparation rules before changing them. Several are generic wave checks whose inputs or exposed bindings are used by subsequent rules. This plan does **not** authorize deleting them merely because they also appear in another package.
3. Update the scenario notes [acoustic 2D](notes_acoustic2d.md) and [acoustic 3D](notes_acoustic3d.md), the FEM model documentation/specification if the declared model-validation behavior changes, and developer guidance for rule generation and ownership. Describe vector length, scalar compatibility, disabled behavior and the validation stage without claiming functionality that has not passed acceptance.

## Verification matrix

Run these against one identified candidate and record the exact commands, hashes, fixtures, expected results, actual diagnostics and tolerances. Compare against the frozen baseline where a behavior must remain unchanged. Tests of isolated JSON fragments establish only that layer; they do not establish a complete editor-to-solver workflow.

1. **Structural and semantic material checks:** For both dimensions and every affected validation entry point, test a valid material; missing density/sound speed; each of the four foreign properties; optional loss factor absent, zero, nonzero and invalid expression; wrong units; unknown symbols; and parameter/frequency/spatial expressions already supported. Test material arrays with multiple entries and correct paths. Compare schema-first and semantic-only behavior to the baseline. Verify that zero and negative density/sound-speed behavior is not changed by this cleanup; separately record solver nonzero rejection without inventing a positivity requirement.
2. **Metadata and package isolation:** Run acoustic 2D alone, acoustic 3D alone, both orders, EM 2D alone, EM 3D alone, mixed acoustic/EM orders and the full eight-scenario registry through browser and actual native composition. Test missing or malformed pressure and `Hz` capability declarations, invalid element order, identity/dimension/physics/catalog errors and duplicate IDs. Acoustic-only must not require `Hz`; applicable electromagnetic validation must still reject a malformed `Hz` declaration. Detect stale ASTs and mismatched authored/compiled programs.
3. **Boundary validation:** For 2D and 3D test enabled vector sizes 0, 1, expected and expected+1; non-array and malformed components; absent vector with legacy scalar; zero/nonzero companion; invalid, complex, coordinate- and frequency-dependent expressions; correct/incorrect units; multiple boundaries; disabled and re-enabled invalid vectors. Compare browser and native error paths and solver rejection. Include another declared vector scenario and any declared alternative input paths in the generic mechanism's regression tests.
4. **Numerical and behavior preservation:** For each acoustic dimension, compare scalar normal velocity with an analytically equivalent Cartesian vector on differently oriented facets, including an oblique facet and reversed vertex orders. Compare assembled loads and solved fields against baseline within recorded tolerances. Include Dirichlet and impedance conditions, nonzero incident fields, periodic mapping, Domain Sources, parameter/frequency-dependent material expressions and both supported sparse backends where available. Test source-free cases and verify no change to global sparse matrix representation or reusable pattern behavior.
5. **Editor and deployment:** In a disposable project, add, edit, disable, enable, save and reopen Neumann conditions; confirm component labels/count, legacy scalar input and visible diagnostics. Validate, mesh and run a representative acoustic Study in each dimension. Build an isolated candidate with matching executable, DLLs, schema, scenario packages and FEM-local WASM; verify hashes and generated-rule freshness. Exercise the identified installed older Store host against the candidate without overwriting it, and identify the exact host version. Do not infer Store compatibility merely from a local browser or a native unit test.
6. **Cross-scenario regression:** Run applicable existing scenario registry, model/schema, boundary-input, scenario-plan, sparse assembler, periodic and Domain Source tests. Explicitly validate an electromagnetic electric incident field with correct and incorrect three-component polarization after the acoustic copies are removed. Verify thermal and elastic package composition and existing model validation. Compare accepted/rejected cases, not just test counts.

## Completion criteria

Complete only when the selected removals preserve every supported validation entry point or an explicitly documented, agreed compatibility change; acoustic-only native metadata no longer requires `Hz`; electromagnetic `Hz` and electric polarization remain protected; Neumann lengths are checked from declarations before solve while legacy valid inputs remain valid; and browser, native, package and Store-host acceptance pass on the same candidate. Keep any unproven deletion or unsupported generic case out of the change and report the exact open gate. Do not stage or install the candidate over the user's running runtime as part of verification.

## Implementation checkpoint

- The acoustic packages no longer contribute the electric-only polarization-count rule or the stray `Hz` metadata check. Each declares its `pressure` order check; `em-2d` owns its `Ez` and `Hz` checks and `em-3d` its `electric` check. The same declaration-driven order-check generator is opted into by all eight scenarios. An actual native metadata-context test exercises each scenario independently and rejects a changed declared order.
- All eight scenarios opt into generated semantic component-count checks for their boundary-vector paths and generated metadata checks for declared formulation orders. Counts derive from `boundaryInputs`; build checks catch stale generated rules and inconsistent defaults/layouts. Enabled wrong-length primary vectors are rejected by browser and native semantic rule programs. The declared EM 3D legacy array fallback is checked when the primary vector is absent, without rejecting scalar values. The solver keeps its defensive check. See [scenario validation alignment](validation_alignment_scenarios.md).
- The six acoustic material obligations remain. Their structural equivalents do not preserve the supported semantic-only entry point or its diagnostics by themselves; deleting them without an equivalent generic replacement would weaken that entry point. The independent loss-factor, quantity-expression and Study rules remain. This is an open consolidation item rather than a claimed removal.
- Follow-up: the Store 0.2.2.0 host opens a malformed-length vector in the editor. Turning “Specify field components” off and on recreates declared defaults; validation passes after applying the corrected vector. This explicitly replaces the prior component values. Semantic-only validation reports a type error for non-array vectors, and component wildcard rules are guarded.
- Focused JavaScript tests cover the eight scenarios' primary counts, the EM 3D array fallback and browser/native-style rule programs; native tests cover isolated scenario metadata. The full native binary suite, 17 Gmsh geometry tests and existing scenario/thermal/Domain Source checks passed during development. Both acoustic examples ran through the isolated Store-host copy; the final aligned candidate was reloaded and completed the acoustic 3D Study there. Wrong-length examples were rejected at structural validation. Tests of all mixed registry orders, every backend and every numerical case in the verification matrix remain open. The candidate and test server are isolated and were not staged over the user's running runtime.
